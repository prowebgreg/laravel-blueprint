# Subagent-Driven Development

Execute Speckit tasks by dispatching fresh subagent per task, with code review after each.

**Core principle:** Fresh subagent per task + review between tasks = high quality, fast iteration

## Overview

This skill works with Speckit artifacts generated by:

- `/speckit.specify` → `spec.md` (user stories, requirements)
- `/speckit.plan` → `plan.md` + `research.md` + `data-model.md` + `contracts/`
- `/speckit.tasks` → `tasks.md` (executable task list with subagent assignments)

**Benefits:**

- Same session (no context switch)
- Fresh subagent per task (no context pollution)
- Code review after each task (catch issues early)
- Faster iteration (no human-in-loop between tasks)
- Specialized expertise per task (subagent matching)

**Execution model:** One task at a time (sequential). The `[P]` markers in tasks.md indicate tasks that _could_ run in parallel, but this skill executes them sequentially to maintain:

- Clear progress tracking
- Focused code reviews
- Predictable state between tasks

**When to use:**

- Tasks are generated via `/speckit.tasks`
- Want continuous progress with quality gates
- Prefer thorough review over speed

**When NOT to use:**

- Need plan revision (run `/speckit.plan` first)
- Tasks not yet generated (run `/speckit.tasks` first)
- Need maximum speed (consider parallel subagents, but lose review gates)

## Speckit Artifacts Structure

```
specs/[###-feature-name]/
├── spec.md           # Feature specification (user stories P1, P2, P3)
├── plan.md           # Implementation plan (tech stack, architecture)
├── research.md       # Technical research and decisions
├── data-model.md     # Entity definitions
├── contracts/        # API contracts (OpenAPI/GraphQL)
├── quickstart.md     # Test scenarios
├── tasks.md          # Task list with subagent assignments (this skill uses this)
└── checklists/       # Quality checklists
```

## Speckit Task Format

Tasks in `tasks.md` follow this format:

```
- [ ] T001 [P] [US1] Description with file path → @subagent-name [, @subagent-name...]
```

- **Checkbox**: `- [ ]` (incomplete) or `- [X]` (complete)
- **Task ID**: Sequential (T001, T002, T003...)
- **[P]**: Parallelizable (different files, no dependencies)
- **[US#]**: User story label (US1, US2, US3 from spec.md priorities)
- **Description**: Action with exact file path
- **Subagent(s)**: `→ @subagent-name` - one or more assigned subagents
  - Single: `→ @laravel-specialist`
  - Multiple: `→ @laravel-specialist, @postgres-pro` (comma-separated, executed in order)

## The Process

**Sequential execution loop:**

```
┌─────────────────────────────────────────────────────────┐
│  For each task in tasks.md:                             │
│                                                         │
│    1. Extract subagent(s) from task (→ @agent1, @agent2)│
│    2. For each subagent in order:                       │
│       a. Dispatch subagent with context                 │
│       b. Subagent implements/enhances                   │
│       c. Pass results to next subagent (if any)         │
│    3. Dispatch code-reviewer subagent                   │
│    4. If issues: dispatch fix subagent, repeat review   │
│    5. Mark task [X] in tasks.md                         │
│    6. Move to next task                                 │
│                                                         │
│  After each phase: checkpoint review                    │
│  After all phases: final review                         │
└─────────────────────────────────────────────────────────┘
```

**Single-agent task flow:**
```
@laravel-specialist → @code-reviewer → [fix if needed] → [X] complete
```

**Multi-agent task flow:**
```
@laravel-specialist → @postgres-pro → @code-reviewer → [fix if needed] → [X] complete
         ↓                  ↓
   Implement core    Optimize queries
```

### 1. Load Speckit Artifacts

Read the feature directory and create TodoWrite with all tasks:

```
1. Run: .specify/scripts/bash/check-prerequisites.sh --json --require-tasks --include-tasks
2. Parse: FEATURE_DIR, tasks content
3. Read: tasks.md, plan.md, spec.md
4. Create TodoWrite from tasks.md phases
```

### 2. Execute Task with Assigned Subagent(s)

For each task, use the subagent(s) assigned in tasks.md (the `→ @subagent-name` suffix).

#### Single-Agent Tasks

**Dispatch fresh subagent:**

```
Task tool:
  subagent_type: [subagent-from-task]
  description: "Implement T00X: [task description]"
  prompt: |
    You are implementing task T00X from specs/[feature]/tasks.md

    ## Task
    - [ ] T00X [P] [US#] [exact task description from tasks.md]

    ## Context
    Read these Speckit artifacts for context:
    - specs/[feature]/plan.md (tech stack, architecture)
    - specs/[feature]/spec.md (user stories, requirements)
    - specs/[feature]/data-model.md (entities, if relevant)
    - specs/[feature]/contracts/ (API specs, if relevant)

    ## Your job
    1. Implement exactly what the task specifies
    2. Follow the file path indicated in the task
    3. Write tests if task is in a test phase
    4. Verify implementation works
    5. Report back with summary

    Working directory: [repo root]

    Report back:
    - What you implemented
    - Files changed/created
    - Tests written and results (if applicable)
    - Any issues or blockers
```

#### Multi-Agent Tasks

For tasks with multiple agents (e.g., `→ @laravel-specialist, @postgres-pro`), execute sequentially:

**First agent (primary implementation):**
```
Task tool:
  subagent_type: laravel-specialist
  description: "Implement T00X: [task description]"
  prompt: |
    You are the PRIMARY implementer for task T00X.

    ## Task
    - [ ] T00X [US#] [task description] → @laravel-specialist, @postgres-pro

    ## Your role
    You are the first of 2 agents. Implement the core functionality.
    The next agent (@postgres-pro) will optimize database aspects.

    [... context and instructions ...]
```

**Subsequent agent(s) (enhance/optimize):**
```
Task tool:
  subagent_type: postgres-pro
  description: "Optimize T00X: [task description]"
  prompt: |
    You are ENHANCING task T00X after the primary implementation.

    ## Previous agent's work
    @laravel-specialist implemented:
    - [Summary of what was done]
    - Files: [list of files changed]

    ## Your role
    Review and optimize the database aspects:
    - Query optimization
    - Index recommendations
    - Schema improvements

    Build on the existing implementation. Do not rewrite unless necessary.

    Report back:
    - What you enhanced/optimized
    - Files modified
    - Performance improvements made
```

**Subagent reports back** with summary of work.

### 3. Review Subagent's Work

**Dispatch code-reviewer subagent:**

```
Task tool:
  subagent_type: code-reviewer
  description: "Review T00X implementation"
  prompt: |
    Review the implementation of task T00X.

    ## What was implemented
    [Summary from implementation subagent's report]

    ## Task requirement
    From specs/[feature]/tasks.md:
    - [ ] T00X [P] [US#] [task description]

    ## User story context
    From specs/[feature]/spec.md:
    [Relevant user story and acceptance scenarios]

    ## Review scope
    Compare git changes: git diff [base-sha]..[head-sha]
    Or review files: [list of changed files]

    ## Review criteria
    1. Does implementation meet task requirements?
    2. Does it satisfy the user story acceptance scenarios?
    3. Code quality and best practices
    4. Security considerations
    5. Test coverage (if applicable)
    6. Performance implications

    ## Output format
    - **Strengths**: What's done well
    - **Issues**:
      - Critical (must fix): [list]
      - Important (should fix): [list]
      - Minor (nice to fix): [list]
    - **Assessment**: Ready / Needs fixes
```

**Code reviewer returns:** Strengths, Issues (Critical/Important/Minor), Assessment

### 4. Apply Review Feedback

**If issues found:**

- Fix Critical issues immediately
- Fix Important issues before next task
- Note Minor issues for later

**Dispatch follow-up subagent if needed:**

```
Task tool:
  subagent_type: [same-subagent-as-implementation]
  description: "Fix review issues for T00X"
  prompt: |
    Fix the following issues from code review for task T00X:
    [list of issues]

    Files to modify: [files]

    Report back when fixed.
```

### 5. Mark Complete, Next Task

- Mark task as completed in TodoWrite
- **Update tasks.md**: Change `- [ ]` to `- [X]` for completed task
- Record the commit SHA for this task
- Move to next task
- Repeat steps 2-5

### 6. Phase Checkpoint Reviews

After completing each Speckit phase, dispatch code-reviewer for phase validation:

```
Task tool:
  subagent_type: code-reviewer
  description: "Review Phase N completion"
  prompt: |
    Review completion of Phase N from specs/[feature]/tasks.md.

    ## Phase tasks
    [List all tasks in this phase with their completion status]

    ## Phase goal
    [From tasks.md phase header - e.g., "User Story 1 - [Title] (Priority: P1)"]

    ## Independent test
    [From tasks.md - "How to verify this story works on its own"]

    ## Review criteria
    1. All phase tasks completed correctly
    2. Phase goal achieved
    3. Independent test passes
    4. No regressions to previous phases
    5. Ready for next phase

    ## Output
    - Phase completion status
    - Any blockers for next phase
    - Verdict: Phase complete / Needs work
```

### 7. Final Review

After all phases complete, dispatch final code-reviewer:

```
Task tool:
  subagent_type: code-reviewer
  description: "Final review of complete implementation"
  prompt: |
    Perform final review of the complete implementation.

    ## Speckit artifacts
    - specs/[feature]/spec.md (requirements)
    - specs/[feature]/plan.md (architecture)
    - specs/[feature]/tasks.md (all tasks should be [X])

    ## All changes
    git diff [initial-sha]..[final-sha]

    ## Review criteria
    1. All tasks in tasks.md marked [X]
    2. All user stories from spec.md satisfied
    3. Architecture matches plan.md
    4. Security best practices followed
    5. Performance requirements met

    ## Output
    - Task completion checklist (all [X])
    - User story verification (P1, P2, P3...)
    - Architecture consistency
    - Any remaining concerns
    - Final verdict: Ready to merge / Needs work
```

### 8. Complete Development

After final review passes:

1. Run full test suite (per tech stack from plan.md)
2. Run linting
3. Run build
4. Verify all tasks in `tasks.md` are marked `[X]`
5. Present summary to user with options:
   - Create PR
   - Commit and push
   - Additional testing needed

## Providing Context to Subagents

When dispatching subagents, provide appropriate context from Speckit artifacts:

**Always include:**
- The exact task from tasks.md
- Path to plan.md (tech stack reference)

**Include when relevant:**
- spec.md for user story context
- data-model.md for entity work
- contracts/ for API work
- research.md for technical decisions

**Context loading strategy:**
- Load only necessary portions
- Summarize long sections
- Reference file paths for subagent to read

## Advantages

**vs. `/speckit.implement` (single agent):**

- Fresh subagent context per task (no confusion)
- Specialized expertise per task type
- Code review gates between tasks

**vs. Manual execution:**

- Automatic quality gates
- Clear task boundaries from Speckit
- Parallel-safe (subagents don't interfere)

**Cost:**

- More subagent invocations
- But catches issues early (cheaper than debugging later)

## Red Flags

**Never:**

- Skip code review between tasks
- Proceed with unfixed Critical issues
- Start next task before current task is reviewed and marked `[X]`
- Implement without reading Speckit artifacts
- Forget to mark tasks `[X]` in tasks.md
- Use a subagent not assigned in the task

**Parallel execution (rare):**

- Only consider for truly independent tasks (different files, no shared state)
- Loses the review-between-tasks benefit
- Risk of merge conflicts and inconsistent state
- If needed, dispatch at most 2-3 subagents, never more

**If subagent fails task:**

- Dispatch fix subagent with specific instructions
- Don't try to fix manually (context pollution)
- Don't move to next task until current is resolved

**If task is blocked (external dependency, waiting on API, etc.):**

- Mark task with `[BLOCKED: reason]` in tasks.md instead of `[X]`
- Skip to next task that isn't dependent on blocked task
- Return to blocked tasks when blocker is resolved
- Example: `- [BLOCKED: waiting for API credentials] T015 [US2] Implement payment webhook → @payment-integration`

**Resuming interrupted session:**

- `tasks.md` tracks progress with `[X]` marks
- When resuming, read tasks.md and continue from first unchecked task
- Recreate TodoWrite from remaining tasks

1. Tech stack from plan.md
2. Task domain (database, API, frontend, etc.)
3. Task type (setup, implementation, testing, etc.)
